# مشخصات نیازمندی‌های نرم‌افزار (SRS)
## دستیار صوتی «همرازشو» (Hamrazsho Voice Assistant)

**نسخهٔ سند:** ۱.۰
**وضعیت:** پیش‌نویس، برگرفته از تجمیع کامل درخواست‌های کارفرما در طول توسعهٔ اسکلت اولیهٔ محصول
**زبان سند:** فارسی

---

## ۱. مقدمه

### ۱.۱ هدف سند
این سند تمام نیازمندی‌های عملکردی و غیرعملکردیِ دستیار صوتی «همدم» را که تا این مرحله توسط کارفرما درخواست شده، به‌صورت یکجا، ساختاریافته و قابل‌ردیابی مستند می‌کند. هدف اصلی، تبدیل مجموعه‌ای از درخواست‌های پراکندهٔ گفتاری/متنی (که در طول یک نشست توسعهٔ تعاملی با دستیار برنامه‌نویسی Claude Code داده شده‌اند) به یک مرجع رسمی و قابل‌استناد برای توسعهٔ آینده، بازبینی محصول، و ارتباط با تیم‌های فنی/حقوقی/بالینی احتمالی است.

### ۱.۲ دامنه محصول
«همدم» یک دستیار صوتی/متنی چندمنظوره است که قرار است طیف وسیعی از نیازهای شخصی، عاطفی، خانوادگی، اجتماعی و اداریِ کاربر را — از غربالگری اولیهٔ سلامت روان تا مدیریت کارهای روزمره مانند ارسال ایمیل — پوشش دهد. نسخهٔ اولیهٔ پیاده‌سازی‌شده (اسکلت نمایشی) با فناوری Expo (React Native + `react-native-web`) روی سه پلتفرم iOS، Android و وب اجرا می‌شود، بدون هیچ بک‌اند واقعی، و با داده‌های کاملاً ساختگی (synthetic).

### ۱.۳ مخاطبان سند
- کارفرما/صاحب محصول
- تیم توسعهٔ نرم‌افزار (فعلی و آینده)
- مشاوران بالینی/روان‌شناسی (برای بازبینی محتوای حساس مانند غربالگری و بحران)
- مشاور حقوقی (برای بررسی مسائل مالکیت معنوی، حریم خصوصی، و مسئولیت)

### ۱.۴ تعاریف، اختصارات و واژگان
| واژه | توضیح |
|---|---|
| SRS | Software Requirements Specification — مشخصات نیازمندی‌های نرم‌افزار |
| STT | Speech-to-Text — تبدیل گفتار به متن |
| TTS | Text-to-Speech — تبدیل متن به گفتار |
| داده ساختگی (Synthetic Data) | داده‌ای که برای نمایش/تست تولید شده و متعلق به هیچ فرد یا موجودیت واقعی نیست |
| اسکلت (Scaffold) | نسخهٔ نمایشیِ اولیهٔ محصول، فاقد بک‌اند و سرویس‌های واقعیِ شخص ثالث |
| FR | Functional Requirement — نیازمندی عملکردی |
| NFR | Non-Functional Requirement — نیازمندی غیرعملکردی |

### ۱.۵ روش گردآوری این سند
این سند از تجمیع **کامل و بدون حذف** تمام پیام‌های کارفرما که هرکدام یک ویژگی یا تغییر جدید درخواست کرده‌اند، تهیه شده است. برای هر درخواست، متن اصلی (در صورت در دسترس‌بودن عیناً) در «پیوست الف» آمده و در بخش ۳ به یک نیازمندی عملکردیِ رسمی (FR) ترجمه شده است. هرجا متن دقیق و کامل یک درخواست در دسترس نبوده، این موضوع صریحاً در پیوست الف قید شده تا سند هرگز چیزی را به‌عنوان نقل‌قول مستقیم جا نزند که نیست.

## ۲. توصیف کلی محصول

### ۲.۱ دیدگاه کلی
«همدم» قرار است نقش یک همراه صوتیِ همه‌کاره را ایفا کند: از سلامت روان و جسم گرفته تا روابط خانوادگی، مسیر شغلی، سرگرمی کودکان، و حتی انجام کارهای اداری روزمره (ایمیل، پیامک، تماس). محصول باید هم با **صدا** و هم با **تایپ** قابل‌استفاده باشد و صدا هرگز نباید پیش‌نیاز اجباری برای استفاده از هیچ قابلیتی باشد.

### ۲.۲ اصول طراحی و فلسفهٔ صداقت (بسیار مهم)
در طول توسعه، یک اصل بنیادین و تکرارشونده حاکم بوده که باید در تمام توسعه‌های آینده نیز رعایت شود:

> **هیچ قابلیتی که واقعاً وجود ندارد، نباید وانمود شود که وجود دارد.**

مصداق‌های این اصل که در محصول فعلی پیاده‌سازی شده‌اند:
- محصول به **هیچ مدل زبانی زندهٔ هوش مصنوعی (LLM)** متصل نیست؛ تمام «گفتگوها» بر پایهٔ بانک سؤال از‌پیش‌نوشته‌شده، تشخیص کلیدواژه، و پاسخ‌های آماده کار می‌کنند.
- محصول به **هیچ سرویس واقعی شخص ثالث** (Spotify، Gmail، Twilio، کاتالوگ کتاب، آرشیو موسیقی واقعی) متصل نیست؛ هرجا چنین قابلیتی خواسته شده، یا با داده‌ی ساختگی شبیه‌سازی شده، یا یک نقطهٔ اتصال مستندشده (Stub) برای آیندهٔ واقعی طراحی شده است.
- محصول **هرگز بدون تأیید نهاییِ کاربر، پیامکی ارسال نمی‌کند، تماسی برقرار نمی‌کند یا ایمیلی نمی‌فرستد** — این یک مرز ایمنی عمدی است، نه یک محدودیت فنی موقت.
- محتوای موسیقی، داستان و «لیریکس» در این اسکلت **کاملاً ساختگی و اورجینال** است تا هیچ نقض مالکیت معنوی‌ای رخ ندهد؛ پیشنهادهای «کتاب» فقط ژانر/موضوع معرفی می‌کنند، نه عنوان یا نویسندهٔ واقعی مشخص.

### ۲.۳ کاربران و ذی‌نفعان
- کاربر نهایی عمومی (بزرگسال، نوجوان، کودک به‌صورت غیرمستقیم از طریق والدین در بخش قصه‌گویی)
- والدین/مراقبان (در بخش پایش مراقبت از کودک)
- کارفرما/صاحب محصول

### ۲.۴ محیط‌های اجرا و پلتفرم
- iOS
- Android
- وب (مرورگر)
یک پایگاه کد واحد (Expo / React Native + react-native-web) برای هر سه پلتفرم.

### ۲.۵ معماری کلی (وضعیت فعلیِ اسکلت)
- بدون بک‌اند؛ تمام منطق سمت کلاینت اجرا می‌شود.
- ذخیره‌سازی محلی روی دستگاه (AsyncStorage) برای هر داده‌ای که باید بین نشست‌ها باقی بماند (پروفایل‌ها، مخاطبین، تاریخچهٔ حال‌وهوا، و غیره).
- صدا: `expo-speech` برای تبدیل متن‌به‌گفتار (هر سه پلتفرم)؛ Web Speech API برای تبدیل گفتار‌به‌متن (فقط مرورگرهای پشتیبان)؛ بازگشت خودکار به تایپ در غیر این صورت.
- داده‌های نمایشی/تستی به‌صورت اسکریپت (`generateSyntheticData.ts`) تولید و در کنسول چاپ می‌شوند.

### ۲.۶ محدودیت‌های بنیادین (خارج از کنترل تیم توسعه)
این محدودیت‌ها واقعیت‌های فنی/قانونی هستند، نه انتخاب‌های دلخواه تیم توسعه:
- **قوانین سیستم‌عامل:** اپل هرگز اجازهٔ ارسال خودکار پیامک یا برقراری خودکار تماس بدون بازشدن اپ خودش را به هیچ اپی نمی‌دهد؛ گوگل نیز چنین اجازه‌ای را فقط به اپی می‌دهد که «اپ پیش‌فرض پیامک‌رسان» گوشی باشد.
- **مالکیت معنوی:** هیچ آهنگ، متن ترانه یا کتاب واقعی نباید بدون مجوز در محصول بازتولید یا با تغییرات جزئی «دور زده» شود.
- **حساسیت داده‌های سلامت روان:** هیچ ابزار غربالگری در این محصول جایگزین تشخیص متخصص نیست و باید همیشه به همراه سلب مسئولیت صریح ارائه شود.
- **زیرساخت‌های ارتباطی واقعی (ایمیل خودکار، پیامک انبوه):** نیازمند سرویس‌های دارای مجوز (مثل Gmail API، Twilio) و رضایت رسمی حساب کاربری هستند، نه چیزی که از سمت کلاینت به‌تنهایی قابل‌پیاده‌سازیِ امن باشد.

## ۳. الزامات عملکردی

> هر نیازمندی به یک یا چند درخواست اصلیِ کارفرما (پیوست الف) ارجاع دارد. جدول ردیابی کامل در «پیوست ب» آمده است.

### FR-01 — غربالگری اولیهٔ سلامت روان
**مرجع:** پیام #۱ (پیوست الف)
**شرح:** دستیار باید با ۵ تا ۱۰ پرسش‌وپاسخ صوتی/متنی، دسته‌بندی‌های مختلف بیماری‌های روانی (افسردگی، اضطراب فراگیر، دوقطبی، ADHD، PTSD، وسواس، بی‌خوابی، اختلال خوردن، طیف روان‌پریشی، بزرگسالان دارای اوتیسم، فرسودگی شغلی و…) را غربالگری کند و برای هرکدام یک «شاخص احتمال» عددی (نه تشخیص قطعی) ارائه دهد.
**قوانین کسب‌وکار کلیدی:**
- سؤالات هسته ثابت‌اند؛ سؤالات تکمیلی بر اساس بالاترین امتیاز خوشه، تطبیقی انتخاب می‌شوند.
- علائم حرکتی/عصبی (مثلاً شبیه پارکینسون) هرگز به‌عنوان درصد روانی امتیاز داده نمی‌شوند؛ فقط ارجاع فوری به پزشک متخصص مغزواعصاب داده می‌شود.
- در هر مرحله، پاسخ‌های ایمنی/خودکشی بررسی می‌شوند و در صورت تشخیص ریسک، گفتگو فوراً به مسیر بحران (FR ذیل) هدایت می‌شود.
**وضعیت:** پیاده‌سازی‌شده.

### FR-02 — تشخیص بحران و پاسخ اورژانسی روانی
**مرجع:** پیام #۱
**شرح:** تشخیص افکار/قصد خودکشی از روی پاسخ‌های مقیاس ایمنی یا متن آزاد (کلیدواژه‌یابی فارسی/انگلیسی)، و در صورت تشخیص، نمایش فوری شماره‌های کمک اورژانسی و یک تمرین تنفس، **پیش از** هرگونه محتوای سبک‌تر مانند جوک یا موسیقی آرام‌بخش (که فقط به‌عنوان کمک ثانویه، بعد از منابع بحران ارائه می‌شوند).
**وضعیت:** پیاده‌سازی‌شده.

### FR-03 — موسیقی متناسب با حال‌وهوا
**مرجع:** پیام #۱
**شرح:** بر اساس نتیجهٔ غربالگری یا حال‌وهوای انتخابی، یک پلی‌لیست مناسب از کاتالوگ موسیقی پیشنهاد و پخش شود.
**محدودیت:** کاتالوگ کاملاً ساختگی است (نام خواننده/آهنگ واقعی نیست) تا نقض مالکیت معنوی رخ ندهد.
**وضعیت:** پیاده‌سازی‌شده.

### FR-04 — توصیه‌های سبک زندگی/مکمل
**مرجع:** پیام #۱
**شرح:** ارائهٔ توصیه‌های عمومی سبک زندگی متناسب با نتیجهٔ غربالگری، همیشه همراه با سلب مسئولیت «این نسخهٔ پزشکی نیست».
**وضعیت:** پیاده‌سازی‌شده.

### FR-05 — موسیقی مورد علاقه (جستجو و دسته‌بندی)
**مرجع:** پیام #۲
**شرح:** یافتن، دسته‌بندی و پخش موسیقی مورد علاقهٔ کاربر بر پایهٔ سه محور: باکلام/بی‌کلام، ایرانی/خارجی، و ژانر/هنرمند موردعلاقه.
**محدودیت:** بدون اتصال واقعی به اینترنت/سرویس پخش؛ جستجوی «اینترنتی» یک نقطهٔ اتصال مستندشده (Stub) برای سرویس واقعی آینده (Spotify، YouTube Music، رادیو جوان و…) است.
**وضعیت:** پیاده‌سازی‌شده.

### FR-06 — راهنمای صوتی گام‌به‌گام آشپزی
**مرجع:** پیام #۳
**شرح:** ارائهٔ رسپیِ غذاهای ایرانی و بین‌المللی (اروپایی، آمریکایی، چینی، فنلاندی، تایوانی و…) و راهنمایی گام‌به‌گام صوتی هنگام پخت، با دستورهای صوتی «بعدی»، «تکرار کن»، «قبلی»، «تمام کن».
**وضعیت:** پیاده‌سازی‌شده.

### FR-07 — قصه‌گویی برای کودکان
**مرجع:** پیام #۴
**شرح:** پرسیدن ردهٔ سنی و جنسیت کودک، سپس روایت قصه با یکی از دو سبک صدا/لحن: «مادرانه» یا «معمولی».
**وضعیت:** پیاده‌سازی‌شده.

### FR-08 — مشاورهٔ زناشویی و روابط
**مرجع:** پیام #۵
**شرح:** ارائهٔ مشاورهٔ روابط برای چهار گروه (زن متأهل، مرد متأهل، دختر مجرد در حال ازدواج، پسر مجرد در حال ازدواج) با پرسش‌وپاسخ تطبیقی و ارائهٔ راهکار برگرفته از (الف) خلاصه‌های اورجینالِ الهام‌گرفته از رویکردهای شناخته‌شدهٔ روان‌شناسی (با ذکر منبع)، و (ب) ضرب‌المثل‌های فارسی، همراه با پاسخ صوتی.
**قانون ایمنی کلیدی:** یک سؤال ایمنی رابطه همیشه پرسیده می‌شود؛ در صورت تشخیص خشونت/کنترل شدید، مسیر به «ایمنی رابطه» (منابع حرفه‌ای/حقوقی) منحرف می‌شود، نه راهکار عمومی.
**وضعیت:** پیاده‌سازی‌شده.

### FR-09 — تغذیه و تناسب اندام بر اساس BMI
**مرجع:** پیام #۶
**شرح:** پرسش وضعیت ورزشکاربودن، هدف (سلامتی/حرفه‌ای)، هدف وزنی، قد و وزن؛ محاسبهٔ BMI و ارائهٔ راهکارهای تغذیه/ورزش متناسب.
**قانون ایمنی کلیدی:** برای ورزشکاران، هشدار محدودیت BMI (نادیده‌گرفتن توده عضلانی)؛ برای تضادهای نگران‌کننده (مثل کمبود وزن + هدف کاهش بیشتر)، ارجاع به پزشک/متخصص تغذیه.
**وضعیت:** پیاده‌سازی‌شده.

### FR-10 — گوش فعال و پاسخ اورژانسی محیطی
**مرجع:** پیام #۷
**شرح:** قابلیتی اختیاری (پیش‌فرض خاموش) که با تشخیص عبارات کلیدی مرتبط با دعوا/درگیری، آتش‌سوزی، یا وضعیت پزشکی اورژانسی از گفتار محیط، پیام مناسب صوتی اعلام کرده، آدرس را از روی موقعیت مکانی می‌خواند، و دکمهٔ تماس با ۱۱۰ (پلیس)، ۱۲۵ (آتش‌نشانی) یا ۱۱۵ (اورژانس) را نمایش می‌دهد.
**محدودیت حیاتی:** این قابلیت **تشخیص صوتی/آکوستیک واقعی نیست** (صدای دعوا/آتش/گریه را نمی‌شنود؛ فقط جمله‌های تبدیل‌شده به متن را برای کلیدواژه بررسی می‌کند)، فقط وقتی صفحه باز و در پیش‌زمینه است کار می‌کند، و **هرگز خودش و بدون اجازه** تماس نمی‌گیرد یا پیامک نمی‌فرستد — فقط برنامهٔ تماس/پیامک را با اطلاعات آماده باز می‌کند.
**وضعیت:** پیاده‌سازی‌شده.

### FR-11 — هشدار فشار/اجبار به دوست مورد اعتماد
**مرجع:** پیام #۸
**شرح:** دریافت پیشاپیشِ نام و شمارهٔ یک «دوست مورد اعتماد» از طریق پرسش‌وپاسخ؛ در صورتی که «گوش فعال» تشخیص دهد کاربر تحت فشار/اجبار قرار دارد، امکان ارسال پیامک «با من تماس بگیر، فوری!» به آن دوست فراهم شود.
**وضعیت:** پیاده‌سازی‌شده (به‌عنوان بخشی از قابلیت گوش فعال).

### FR-12 — پایش مراقبت از کودک (نسخهٔ گوش فعال برای پرستار بچه)
**مرجع:** پیام #۹
**شرح:** هنگام فعال‌بودن «گوش فعال» در محیطی مثل مراقبت پرستار بچه، ارسال خلاصهٔ دوره‌ای (هر ۳۰ دقیقه، هر ۶۰ دقیقه، یا به‌صورت دستی) از گفتگوهای شنیده‌شده برای اطلاع والدین.
**محدودیت حیاتی:** خلاصه فقط می‌تواند بگوید «چند گفتگو شنیده شد» و «آیا عبارت نگران‌کننده‌ای در آن‌ها بود» — نه یک قضاوت رفتاری واقعی دربارهٔ خوب/بدبودن رفتار پرستار (نیازمند مدل واقعی تشخیص صدا/رفتار که پیاده‌سازی نشده). ملاحظات حقوقیِ رضایت/اطلاع‌رسانی برای ضبط/پایش فرد دیگر باید پیش از استفادهٔ واقعی بررسی شود.
**وضعیت:** پیاده‌سازی‌شده.

### FR-13 — مشاور استایل و آرایش
**مرجع:** پیام #۱۰
**شرح:** دریافت اطلاعات کاربر (جنسیت، سن، تحصیلات، تأهل، بودجه، دسترسی به آرایشگاه) و یک عکس لحظه‌ای، سپس پیشنهاد یک لوک آرایشی متناسب؛ همچنین دریافت عکس از کمد لباس/کفش و پیشنهاد ترکیب مناسب مناسبت (عروسی، تولد، عزا).
**محدودیت حیاتی:** بدون هوش مصنوعیِ واقعیِ تولید/ویرایش تصویر — پیشنهادها فقط توضیح نوشتاری/صوتی از فهرست از‌پیش‌آماده‌اند، و تطبیق لباس بر اساس برچسب‌هایی است که خود کاربر روی عکس‌ها می‌زند، نه تحلیل تصویری واقعی. عکس‌ها فقط روی گوشی کاربر ذخیره می‌شوند.
**وضعیت:** پیاده‌سازی‌شده.

### FR-14 — ترک اعتیاد (سیگار/الکل/مواد/هر عادت دیگر)
**مرجع:** درخواستی جداگانه دربارهٔ کمک به ترک تدریجی اعتیاد با بازخورد روزانه؛ **متن دقیق و کامل این پیام در دسترس نیست** (نگاه پیوست الف).
**شرح:** پرسش نوع اعتیاد، میزان مصرف، سابقه، محرک‌های اصلی و انگیزهٔ ترک؛ ارائهٔ یک برنامهٔ تدریجیِ چندمرحله‌ای صوتی؛ دریافت چک‌این روزانه (مصرف/عدم‌مصرف، شدت میل) و محاسبهٔ توالی روزهای موفق.
**محدودیت حیاتی:** برای الکل و مواد مخدر، همیشه هشدار می‌دهد که ترک ناگهانی/بدون نظارت می‌تواند خطرناک باشد و ارجاع به پزشک/مرکز ترک اعتیاد ضروری است؛ این بخش هرگز جایگزین سم‌زدایی پزشکی نیست.
**وضعیت:** پیاده‌سازی‌شده.

### FR-15 — مشاور شغلی و کارآفرینی
**مرجع:** پیام #۱۱
**شرح:** تشخیص روحیهٔ «کارمندی» یا «کارآفرینی» از طریق چند سؤال اکتشافی؛ سپس ارائهٔ مسیر متناسب: رزومه‌نویسی و ارسال به شرکت‌ها، کارآموزی/کارورزی، مهارت‌افزایی، فریلنسری، یا راه‌اندازی کسب‌وکار؛ و «دنبال‌کردن» کاربر تا موفقیت نهایی.
**محدودیت حیاتی:** بدون اتصال واقعی به سایت‌های کاریابی؛ «دنبال‌کردن تا موفقیت» به‌صورت یک چک‌لیست نقطه‌عطف و دفترچهٔ پیشرفت محلی (نه سیستم واقعی پیگیری/یادآوری) پیاده‌سازی شده است.
**وضعیت:** پیاده‌سازی‌شده.

### FR-16 — تشخیص آهنگ از روی زمزمه/نام/بخشی از متن
**مرجع:** پیام #۱۲
**شرح:** وقتی کاربر بخشی از آهنگ را می‌خواند، نام آن را می‌گوید، یا بخشی از آن را پخش می‌کند، دستیار آهنگ را (از آرشیو خودش) تشخیص داده و پخش کند، و حتی برای آهنگ خارجی «لیریکس» نشان دهد.
**محدودیت حیاتی (تغییر دامنه نسبت به درخواست اصلی):** هیچ فناوری واقعی تشخیص صدا/اثرانگشت صوتی پیاده‌سازی نشده (فنی و از نظر مالکیت معنوی مخاطره‌آمیز است). آنچه پیاده شده: تطبیق متنی تقریبی (Fuzzy) روی نام آهنگ/خواننده که کاربر می‌گوید یا تایپ می‌کند، فقط با کاتالوگ ساختگیِ همین اپ. «لیریکس»های نمایش‌داده‌شده کاملاً ساختگی و اورجینال‌اند، نه متن ترانهٔ واقعی. نقطهٔ اتصال به سرویس واقعی (ACRCloud/AudD برای تشخیص صدا، Musixmatch/Genius برای لیریکس) به‌صورت Stub مستند شده است.
**وضعیت:** پیاده‌سازی‌شده (با دامنهٔ اصلاح‌شدهٔ فوق).

### FR-17 — رفیق همراه (Companion) / بهترین دوست هوشمند
**مرجع:** پیام #۱۳
**شرح:** یک فضای گفتگوی روزانه که نام و چند «فکت» دربارهٔ کاربر را به خاطر می‌سپارد، حال‌وهوای روزانه را ثبت می‌کند، جملات همدلانهٔ متناسب می‌گوید، خلاصهٔ حال‌وهوای اخیر را یادآوری می‌کند، و به بخش‌های مرتبط اپ (موسیقی، غربالگری، ورزش و…) پیشنهاد می‌دهد.
**محدودیت حیاتی (تغییر دامنه نسبت به درخواست اصلی):** این «رفیق» به هیچ مدل زبانی زندهٔ واقعی وصل نیست و چیزی که کاربر می‌نویسد را واقعاً «نمی‌فهمد» — فقط فکت‌های صریحاً واردشده را ذخیره کرده و از بین جملات از‌پیش‌نوشته‌شده، مناسب‌ترین را بر اساس حال‌وهوای انتخابی برمی‌گزیند. هیچ حافظهٔ گفتگویی بلندمدت یا تحلیل احساسات واقعی از متن آزاد وجود ندارد.
**وضعیت:** پیاده‌سازی‌شده (با دامنهٔ اصلاح‌شدهٔ فوق).

### FR-18 — مشاور موقعیت‌های اجتماعی (شخصیت‌محور)
**مرجع:** پیام #۱۴ (مثال جهیزیه/مادر)
**شرح:** برای موقعیت‌هایی مثل اختلاف با یک عضو خانواده/دوست/همکار، کاربر رابطه، نوع موقعیت (مرز مالی، نصیحت ناخواسته، اختلاف تصمیم، تعارض سخاوت، مرزگذاری، انتظار خانوادگی)، و حداکثر سه ویژگی شخصیتیِ طرف مقابل (دست‌ودل‌باز/خسیس، کنترل‌گر/انعطاف‌پذیر، سنتی/امروزی، احساساتی/آرام) را انتخاب می‌کند؛ دستیار ابتدا یک «برداشت شخصیتی» بازتابی می‌گوید و سپس بهترین راهکار متناسب را ارائه می‌دهد. دیتاست شامل ده‌ها راهکار برای ترکیب‌های مختلف، از جمله دقیقاً مثال جهیزیه/مادر خواسته‌شده، است.
**محدودیت حیاتی:** این بخش هیچ‌کس را واقعاً نمی‌شناسد یا تحلیل روان‌شناختی واقعی انجام نمی‌دهد — فقط بازتاب برچسب‌هایی است که خود کاربر انتخاب کرده.
**وضعیت:** پیاده‌سازی‌شده.

### FR-19 — پیشنهاد هدیه
**مرجع:** پیام #۱۵
**شرح:** شناسایی رابطه با گیرندهٔ هدیه، ردهٔ سنی، مناسبت، بودجه و علایق او؛ پیشنهاد ایده‌های متناسب، از جمله پیشنهاد خرید کتاب برای پوشش «کمبودها»ی گیرنده.
**محدودیت حیاتی:** بدون اتصال به فروشگاه/کاتالوگ محصول واقعی؛ پیشنهادهای کتاب فقط ژانر/موضوع کلی معرفی می‌کنند (نه عنوان/نویسندهٔ واقعی مشخص) تا از ادعای نادرست یا قدیمی دربارهٔ یک اثر واقعی پرهیز شود.
**وضعیت:** پیاده‌سازی‌شده.

### FR-20 — خانواده و اطرافیان (شناخت مستمر افراد پیرامون کاربر)
**مرجع:** پیام #۱۶
**شرح:** ذخیرهٔ مستمر پروفایل افراد اطراف کاربر (خواهر، برادر، همسر، پدر، مادر، فرزند، و هرکس تأثیرگذار دیگر) شامل نام، نوع رابطه، و ویژگی‌های شخصیتی؛ اتصال مستقیم این پروفایل‌ها به «مشاور موقعیت‌های اجتماعی» (FR-18) تا کاربر لازم نباشد هر بار از نو رابطه/شخصیت طرف مقابل را وارد کند.
**محدودیت حیاتی:** مشابه FR-18 — بدون شناخت یا پایش واقعی؛ فقط ذخیرهٔ برچسب‌های انتخابی کاربر.
**وضعیت:** پیاده‌سازی‌شده.

### FR-21 — دستیار کارهای شخصی (ایمیل، پیامک، تماس، واتساپ)
**مرجع:** پیام #۱۷
**شرح:** مانند یک دستیار شخصی، انجام کارهای اداری روزمره از طریق فرمان صوتی/متنی (مثلاً «به مامان پیامک بده بگو دیر میام»): تشخیص نوع کار (ایمیل/پیامک/تماس/واتساپ)، تشخیص مخاطب و متن پیام از روی فرمان، و اجرای عمل پس از تأیید کاربر.
**محدودیت حیاتی و عمدی (تغییر دامنه نسبت به درخواست اصلی «وصل‌شدن به تمامی اپلیکیشن‌ها»):**
- این بخش هرگز به‌جای کاربر ایمیل/پیامک ارسال نمی‌کند یا تماس برقرار نمی‌کند — فقط برنامهٔ بومی مربوطهٔ گوشی (ایمیل، پیامک، تلفن، واتساپ) را با محتوای آماده باز می‌کند؛ لمس نهاییِ «ارسال»/«تماس» همیشه با خود کاربر و داخل همان برنامه است. این هم یک مرز ایمنیِ عمدی است و هم یک واقعیتِ سیستم‌عاملی (بند ۲.۶).
- برای کاهش تعداد تاییدها (بدون تغییر این مرز)، کاربر می‌تواند مخاطبی را «مورد اعتماد» علامت بزند؛ برای چنین مخاطبی، وقتی فرمان از قبل کامل باشد، پرسش تاییدِ داخل اپ حذف می‌شود و مستقیم برنامهٔ مربوطه باز می‌شود (باز هم فقط باز می‌شود، نه ارسال).
- این بخش نمی‌تواند به «هر اپلیکیشنی» وصل شود؛ فقط اپ‌هایی با آدرس بازکردنیِ عمومی (ایمیل، پیامک، تلفن، واتساپ) پشتیبانی می‌شوند.
- «مخاطبین سریع» یک دفترچهٔ آدرس کوچک و محلی است که خود کاربر می‌سازد — نه دسترسی به مخاطبین واقعی گوشی، تاریخچهٔ واقعی ایمیل/پیامک، یا لاگ تماس.
**وضعیت:** پیاده‌سازی‌شده (با دامنهٔ اصلاح‌شدهٔ فوق)، شامل قابلیت «مورد اعتماد» برای کاهش تاییدها.

### FR-22 — اتصال واقعیِ ایمیل از طریق Gmail (OAuth)
**مرجع:** پیام #۲۰ («بریم سراغ Gmail OAuth واقعی»)
**شرح:** فراهم‌کردن مسیری که در آن دستیار بتواند، پس از ورود واقعیِ کاربر با حساب گوگل و یک‌بار اعطای اجازهٔ ارسال ایمیل (Gmail send scope) در صفحهٔ رسمی گوگل، ایمیل را واقعاً و بدون نیاز به بازکردن اپ ایمیل جداگانه ارسال کند.
**پیش‌نیازهای خارج از کنترل تیم توسعه:**
- کارفرما باید شخصاً یک پروژهٔ Google Cloud بسازد، Gmail API را فعال کند، صفحهٔ رضایت OAuth را پیکربندی کند، و یک Client ID واقعی بگیرد (این بخش از هیچ سشن توسعه‌ای به‌جای کارفرما قابل‌انجام نیست، چون نیاز به ورود با حساب گوگل شخصی دارد).
- چون Gmail send یک «Scope حساس» است، در وضعیت انتشار «Testing» فقط تا ۱۰۰ حساب گوگلِ صریحاً اضافه‌شده به‌عنوان کاربر آزمایشی می‌توانند وارد شوند؛ انتشار عمومی نیازمند بازبینی رسمی گوگل (سیاست حریم خصوصی، صفحهٔ اصلی، بررسی چندهفته‌ای) است.
- چون این اسکلت بک‌اندی ندارد، هرگونه پیاده‌سازیِ سمت کلاینت این قابلیت، محدودیت امنیتیِ شناخته‌شده‌ای دارد (کلید محرمانهٔ OAuth باید در داخل بستهٔ کلاینت جاسازی شود؛ راه‌حل امن‌تر نیازمند یک بک‌اند واقعی برای نگه‌داری آن کلید است).
**وضعیت:** در حال بررسی/طراحی — پیاده‌سازی هنوز آغاز نشده.

## ۴. الزامات غیرعملکردی

### NFR-01 — حریم خصوصی و داده
تمام داده‌های کاربر (پروفایل‌ها، مخاطبین، تاریخچهٔ حال‌وهوا، کمد لباس، و…) فقط روی دستگاه خود کاربر (AsyncStorage) ذخیره می‌شوند؛ هیچ داده‌ای به هیچ سروری ارسال نمی‌شود، چون این اسکلت اصلاً بک‌اندی ندارد.

### NFR-02 — امنیت و رضایت کاربر
هیچ اقدام غیرقابل‌بازگشت یا ارتباطی با اشخاص ثالث (ارسال پیامک/ایمیل، برقراری تماس) بدون تأیید صریح کاربر (یا علامت‌گذاری آگاهانهٔ «مورد اعتماد» توسط خود کاربر) انجام نمی‌شود.

### NFR-03 — چندسکویی‌بودن
یک پایگاه کد باید هم‌زمان روی iOS، Android و وب اجرا شود.

### NFR-04 — صدا (ورودی/خروجی)
خروجی صوتی (TTS) باید در هر سه پلتفرم کار کند. ورودی صوتی (STT) در مرورگرهای پشتیبان کار می‌کند و در غیر این صورت باید بی‌درنگ و بدون خطا به تایپ بازگردد؛ صدا هرگز نباید تنها راه استفاده از یک قابلیت باشد.

### NFR-05 — قابلیت تست
هر منطق قابل‌تست (موتورهای تصمیم‌گیری، تجزیهٔ متن، امتیازدهی) باید با تست واحد (Jest) پوشش داده شود؛ یک اسکریپت تولید دادهٔ ساختگی باید برای هر قابلیت جدید، یک سناریوی نمایشی به کنسول اضافه کند.

### NFR-06 — رعایت مالکیت معنوی
هیچ محتوای واقعیِ دارای کپی‌رایت (آهنگ، متن ترانه، متن کتاب) نباید در کد یا داده‌های محصول بازتولید شود، حتی با تغییرات جزئی.

### NFR-07 — پشتیبانی زبانی
حداقل فارسی و انگلیسی باید برای تمام متن‌های رابط کاربری و صدا پشتیبانی شوند.

### NFR-08 — صداقت در ارائهٔ قابلیت (اصل حاکم بر کل محصول)
هر قابلیتی که به‌صورت واقعی پیاده‌سازی نشده (تشخیص صدا، ارسال خودکار واقعی، دسترسی به سرویس‌های شخص ثالث) باید به‌صراحت در رابط کاربری (`Disclaimer`) و در این سند مشخص شود؛ هرگز نباید به کاربر وانمود شود که قابلیتی فراتر از آنچه واقعاً پیاده شده، وجود دارد.

# دستیار همراه ذهن — Mental Wellness Voice Assistant (Scaffold)

یک اسکلت (scaffold) کامل و قابل‌اجرا برای یک دستیار صوتی/متنی سلامت روان، با یک کدبیس React Native
(Expo) که هم‌زمان روی **iOS، Android و وب** اجرا می‌شود.

## ⚠️ اخلی مهم — محدودیت‌ها و مسئولیت (بخوانید)

- این پروژه **یک ابزار خودارزیابی غیرتشخیصی** است، نه یک محصول پزشکی. درصدهای «احتمال» با یک
  الگوریتم امتیازدهی ساده و ابتکاری (heuristic) تولید می‌شوند، نه یک مدل بالینی اعتبارسنجی‌شده.
- سؤالات از روی ساختار پرسش‌نامه‌های شناخته‌شده عمومی (شبیه PHQ-9، GAD-7، ASRS، MDQ، PC-PTSD-5،
  ISI، SCOFF، CAGE-AID) الهام گرفته شده‌اند اما بازنویسی و ساده‌سازی شده‌اند؛ **نسخه رسمی/دارای
  مجوز آن مقیاس‌ها نیستند** و نباید به‌جای آن‌ها بازاریابی شوند.
- بیماری‌هایی مثل **پارکینسون** یک اختلال عصبی-حرکتی هستند، نه روانی، و با پرسش‌وپاسخ صوتی قابل
  غربالگری نیستند. این اپ فقط چند علامت هشدار (لرزش، کندی حرکت، سفتی عضلات) را شناسایی و کاربر را
  به پزشک ارجاع می‌دهد — هرگز امتیاز روان‌پزشکی به آن نمی‌دهد.
- مسیر بحران (Crisis flow) طوری طراحی شده که **همیشه** ابتدا شماره‌های کمک اورژانسی و مشاوره را
  نشان دهد و تماس با فرد مورد اعتماد/اورژانس را تشویق کند؛ موسیقی و جوک فقط به‌عنوان کمک ثانویه
  *بعد از* نمایش منابع کمک واقعی ارائه می‌شوند، نه به‌جای آن‌ها.
- شماره‌های بحران در `src/data/crisisResources.ts` نقطه شروع منطقی هستند اما **باید پیش از هر
  استقرار واقعی، برای منطقه هدف بازبینی و به‌روزرسانی شوند**.
- بخش «مشاورهٔ زناشویی و روابط» راهکارهای عمومی و آموزشی می‌دهد، نه یک جلسهٔ مشاورهٔ واقعی؛ اگر
  پاسخ‌ها نشانهٔ خشونت یا کنترل شدید در رابطه باشد، به‌جای راهکار، کاربر مستقیماً به منابع کمک واقعی
  ارجاع داده می‌شود (`RelationshipSafetyScreen`)، همان‌طور که مسیر بحران خودکشی هم کار می‌کند.
- تمام داده‌های ساختگی این ریپو (کاربران نمونهٔ `npm run generate:synthetic` و غیره) **کاملاً
  مصنوعی (synthetic)** هستند — هیچ داده واقعی بیمار وجود ندارد. یک بک‌اند واقعی هم اکنون وجود دارد
  (پوشهٔ `../backend` — Node/Express/Prisma/Postgres با ورود شماره‌موبایل+OTP)، اما استفاده از آن
  کاملاً اختیاری است و فقط برای پشتیبان‌گیری/همگام‌سازیِ دادهٔ واقعیِ خودِ کاربر به‌کار می‌رود، نه برای
  جمع‌آوری یا تحلیل دادهٔ بیمار؛ جزئیات در «حساب کاربری و همگام‌سازی ابری» پایین‌تر.
- قبل از هر استفادهٔ واقعی: با یک روان‌پزشک/روان‌شناس بالینی و یک متخصص حقوقی/رگولاتوری (به‌خصوص
  درباره مسیر ریسک خودکشی) مشورت کنید.
- «گوش فعال» یک **تشخیص صوتی/آکوستیک واقعی نیست** — فقط کلمات واضح گفته‌شده را که به متن تبدیل
  می‌شوند برای عبارات کلیدی بررسی می‌کند، هرگز خودش با اورژانس تماس نمی‌گیرد یا پیامک نمی‌فرستد (فقط
  برنامهٔ گوشی را با شماره/متن آماده باز می‌کند)، و فقط تا وقتی صفحه باز است کار می‌کند. جزئیات کامل
  در بخش «گوش فعال» پایین‌تر.

### جریان گفتگو (Screening flow)

1. کاربر «گفتگوی کامل» (تا ۱۰ سؤال) یا «سریع» (۵ سؤال) را انتخاب می‌کند.
2. ۶ تا ۸ سؤال هسته به ترتیب ثابت پرسیده می‌شوند: افسردگی، دو سؤال ایمنی/ریسک خودکشی (همیشه
   پرسیده می‌شوند)، اضطراب فراگیر، ADHD، بی‌خوابی، PTSD، و یک سؤال ارجاعی برای علائم حرکتی/عصبی.
3. اگر حالت «کامل» باشد، موتور بر اساس بالاترین امتیاز خوشه‌ها (افسردگی، اضطراب، ADHD، بی‌خوابی،
   PTSD) تا ۲ سؤال تکمیلی تطبیقی می‌پرسد (مثلاً افسردگی بالا → بررسی دوقطبی).
4. بعد از هر پاسخ، `crisisDetector` بررسی می‌کند؛ اگر ریسک تشخیص داده شود، گفتگو بلافاصله متوقف و
   کاربر به `CrisisScreen` هدایت می‌شود — صرف‌نظر از این‌که چند سؤال باقی مانده.
5. در پایان، `scoreSession` یک درصد «شاخص احتمال» ۰ تا ۱۰۰ برای هر بیماری قابل‌امتیازدهی محاسبه
   می‌کند و ۳ بیماری برتر برای پیشنهاد موسیقی/توصیه استفاده می‌شوند.

### موسیقی مورد علاقه (`FavoriteMusicScreen`)

کاتالوگ موسیقی روی سه محور برچسب‌گذاری شده تا بتوان با هر ترکیبی از آن‌ها جستجو/فیلتر کرد:
حال‌وهوا (mood)، باکلام/بی‌کلام (vocal)، و ایرانی/خارجی (origin) — `src/data/musicCatalog.ts`.
کاربر می‌تواند هنرمند/ژانر موردعلاقه و ترجیح باکلام‌وبی‌کلام/ایرانی‌وخارجی را ثبت کند (ذخیره‌شده
روی دستگاه با AsyncStorage، هرگز به جایی ارسال نمی‌شود)، و `musicSearchEngine.ts`:

- کاتالوگ محلی را بر اساس این علایق **رتبه‌بندی** می‌کند (`recommendForProfile`)،
- نتیجه را در ۴ دستهٔ باکلام‌ایرانی/باکلام‌خارجی/بی‌کلام‌ایرانی/بی‌کلام‌خارجی **دسته‌بندی** می‌کند
  (`categorizeTracks`)،
- و از طریق یک انتزاع `MusicSearchProvider` قابل **جستجو** است.

⚠️ **محدودیت مهم**: این اسکلت به اینترنت یا هیچ سرویس موسیقی واقعی (Spotify، YouTube Music، رادیو
جوان، Apple Music و …) متصل نیست و کلید API ندارد؛ تمام آهنگ‌ها **داده‌های ساختگی با نام‌های کاملاً
جعلی** هستند (برای پرهیز از نقض حق مالکیت معنوی/هویتی). دکمهٔ «جستجوی اینترنتی» در همین صفحه عمداً
به یک ارائه‌دهندهٔ نمایشی (`remoteInternetProvider`) وصل است که خطای صریح می‌دهد، نه این‌که وانمود کند
واقعاً در اینترنت جستجو کرده. برای اتصال واقعی، یک پیاده‌سازی واقعی پشت همین اینترفیس در
`src/engine/musicSearchEngine.ts` بنویسید — بقیهٔ اپ بدون تغییر کار می‌کند.

### راهنمای صوتی آشپزی (`RecipeScreen` + `CookingScreen`)

کاربر یک غذا را از بین ۱۲ آشپزی (ایرانی، فرانسوی، ایتالیایی، آمریکایی، چینی، فنلاندی، تایوانی،
مکزیکی، ژاپنی، هندی، تایلندی، مدیترانه‌ای — `src/data/cuisines.ts` و `recipeCatalog.ts`) انتخاب
می‌کند و دستیار او را **مرحله‌به‌مرحله و با صدا** راهنمایی می‌کند:

1. با شروع پخت، دستیار مرحلهٔ اول را با صدا می‌خواند (و در صورت نبود صدا، به‌صورت نوشتاری هم نشان
   می‌دهد — دقیقاً مثل بقیهٔ اپ، صدا هرگز اجباری نیست).
2. کاربر با صدا یا تایپ می‌گوید «بعدی» / «انجام دادم» تا مرحلهٔ بعد خوانده شود، «تکرار کن» تا همان
   مرحله دوباره گفته شود، «قبلی» تا برگردد، یا «تمام کن» تا آشپزی را متوقف کند —
   `engine/voiceCommands.ts#matchStepCommand` این عبارت‌ها را (فارسی و انگلیسی) تشخیص می‌دهد و
   `state/CookingContext.tsx` وضعیت مرحلهٔ فعلی را همان‌طور پیش می‌برد. همین تابع مشترک، پایهٔ
   دستورهای صوتی قصه‌گویی (پایین) هم هست.
3. با پایان آخرین مرحله، دستیار «نوش جان!» می‌گوید و کاربر می‌تواند به فهرست رسپی‌ها برگردد.

⚠️ **محدودیت مهم**: پایگاه‌دادهٔ رسپی یک **نمونهٔ اولیهٔ ۱۲ موردی و قابل‌گسترش** است، نه یک بانک
اطلاعاتی واقعی و نامحدود از «تمام غذاهای دنیا» — چنین چیزی نیازمند یک سرویس/دیتابیس رسپی واقعی
(مثل Spoonacular یا Edamam) است. طراحی `recipeEngine.ts` عمداً ساده نگه داشته شده تا افزودن رسپی
بیشتر، یا وصل‌کردن یک سرویس واقعی پشت همان تابع `searchRecipes`، بدون تغییر در صفحات اپ ممکن باشد.

### قصه برای کودکان (`StorytellingScreen` + `StoryPlaybackScreen`)

دستیار قبل از هر چیز، مثل یک گفتگوی واقعی، **سن و جنسیت کودک را می‌پرسد** (با صدا یا تایپ، از طریق
دکمه یا جواب آزاد)، سپس می‌پرسد قصه با «صدای مادرانه و مهربان» گفته شود یا «معمولی و ساده»:

1. بر اساس سن (۲ تا ۴، ۵ تا ۷، ۸ تا ۱۰، یا ۱۱ تا ۱۳ سال)، فهرست قصه‌های مناسب همان رده نشان داده
   می‌شود — `src/data/storyCatalog.ts` (۸ قصهٔ کاملاً اورجینال، نوشته‌شده برای همین اپ، نه اقتباس از
   قصه‌های موجود).
2. بر اساس جنسیت انتخابی، یک اسم قهرمان (پسرانه/دخترانه/خنثی) انتخاب و در تمام قصه جایگزین
   `{{NAME}}` می‌شود — `engine/storytellingEngine.ts#pickProtagonistName` + `renderParagraph`.
3. قصه‌گویی، بخش‌به‌بخش و با صدا انجام می‌شود؛ همان دستورهای صوتی آشپزی («ادامه بده»، «تکرار کن»،
   «قبلی»، «تمام کن») اینجا هم کار می‌کنند (`engine/voiceCommands.ts`، مشترک با `CookingContext`).
4. صدای قصه‌گو از طریق `voiceService.speakStory` پخش می‌شود که سعی می‌کند یک **صدای زنانه** روی
   دستگاه پیدا کند و بسته به سبک انتخابی، سرعت و زیروبمی صدا را تنظیم می‌کند: «مادرانه» کندتر و
   کمی زیرتر، «معمولی» با سرعت عادی گفتار.

⚠️ **محدودیت صادقانه دربارهٔ صدای زن**: نه `expo-speech` و نه Web Speech API هیچ فیلد «جنسیت صدا»ی
قابل‌اتکایی روی همهٔ پلتفرم‌ها ارائه نمی‌دهند. انتخاب صدای زنانه در `voiceService.ts` یک حدس مبتنی
بر نام‌های رایج صداهای iOS/Android/مرورگر است (مثل «Samantha»، «Zira»، «زهرا»)، نه یک تضمین قطعی —
روی بعضی دستگاه‌ها ممکن است فقط یک صدا برای هر زبان نصب باشد. برای کنترل دقیق و همیشگی روی صدا،
باید یک سرویس TTS ابری (مثل Google Cloud TTS یا Amazon Polly، که صدای زن فارسی/انگلیسی مشخصی دارند)
پشت همین تابع `speakStory` وصل شود.

### مشاورهٔ زناشویی و روابط (`CounselingScreen` + `CounselingResultsScreen`)

دستیار اول می‌پرسد کاربر در کدام دستهٔ زیر قرار می‌گیرد: **زن متأهل**، **مرد متأهل**، **دختر مجرد
در حال ازدواج**، یا **پسر مجرد در حال ازدواج**؛ این فقط برای متناسب‌کردن سؤال‌ها استفاده می‌شود
(مثلاً سؤال «آمادگی برای ازدواج» فقط برای افراد مجرد پرسیده می‌شود)، نه برای تغییردادن محتوای
راهکارها بر اساس جنسیت.

1. یک گفتگوی پرسش‌وپاسخ تطبیقی (شبیه به بخش غربالگری سلامت روان) دربارهٔ موضوعاتی مثل ارتباط
   کلامی، اعتماد، مسائل مالی، خانوادهٔ همسر، حل تعارض، انتظارات، تصمیم‌گیری مشترک و حسادت انجام
   می‌شود — `src/data/counselingQuestions.ts` + `engine/counselingEngine.ts`.
2. یک سؤال ایمنی **همیشه** پرسیده می‌شود (آیا همسر/نامزدتان با تهدید، کنترل شدید یا آسیب فیزیکی
   شما را ترسانده؟). اگر پاسخ یا متن آزاد نشانهٔ نگران‌کننده‌ای داشته باشد، گفتگو فوراً متوقف و کاربر
   به `RelationshipSafetyScreen` هدایت می‌شود — به‌جای فهرست راهکار، شمارهٔ خط کمک و توصیه به کمک
   حرفه‌ای/حقوقی نشان داده می‌شود. اگر متن آزاد نشانهٔ افکار خودکشی داشته باشد (نه لزوماً خشونت رابطه)،
   کاربر به همان `CrisisScreen` بخش سلامت روان هدایت می‌شود؛ این دو مسیر ایمنی کاملاً مستقل از هم عمل
   می‌کنند.
3. در پایان، بر اساس موضوع(های) با بیشترین نگرانی، چند راهکار از `relationshipStrategies.ts` انتخاب
   و **با صدا خوانده می‌شود** — دقیقاً همان چیزی که خواسته شد: «به‌صورت صوتی راهکار مناسب ارائه شود».

**دیتاست راهکارها**: ترکیبی از ۱۱ نکتهٔ اورجینال الهام‌گرفته از رویکردهای شناخته‌شدهٔ روان‌شناسی
(گاتمن، زوج‌درمانی هیجان‌محور سو جانسون، نظریهٔ دلبستگی جان بالبی، زوج‌درمانی ایماگو هارویل
هندریکس، ارتباط بدون خشونت مارشال روزنبرگ، گوش‌دادن فعال کارل راجرز، رفتاردرمانی شناختی آرون بک،
روان‌شناسی مثبت‌گرای مارتین سلیگمن، نظریهٔ سیستم‌های خانوادهٔ موری باوئن) و ۸ ضرب‌المثل اصیل فارسی
(مثل «زبان سرخ سر سبز می‌دهد بر باد»، «آشپز که دو تا شد...»، «صبر و ظفر هر دو دوستان قدیمند»)، هرکدام
با یادداشتی کوتاه دربارهٔ کاربرد امروزی‌اش. متن هر نکتهٔ روان‌شناسی **خلاصهٔ اورجینالی** است که برای
همین اپ نوشته شده (نه نقل‌قول از کتاب)، همراه با نام رویکرد/فرد به‌عنوان منبع الهام.

⚠️ **محدودیت‌های مهم**:

- این جریان **جایگزین یک جلسهٔ مشاورهٔ واقعی نیست** — `DISCLAIMERS.counselingNotSubstitute` در نتیجه
  همیشه نمایش داده می‌شود.
- دروازهٔ ایمنی (`assessRelationshipSafety`) یک ابزار غربالگری ساده با کلیدواژه و مقیاس است، نه یک
  ارزیابی خطر بالینی؛ برای شرایط واقعی خشونت خانگی، `RelationshipSafetyScreen` صراحتاً کاربر را به
  کمک حرفه‌ای/حقوقی ارجاع می‌دهد و هیچ توصیهٔ خاصی دربارهٔ «چه‌کار کند» نمی‌دهد (چون برنامه‌ریزی ایمنی
  نیازمند تخصص و شناخت کامل شرایط فرد است).
- شماره‌های `src/data/crisisResources.ts` (از جمله خط ملی خشونت خانگی آمریکا) باید پیش از هر استقرار
  واقعی، برای منطقهٔ هدف بازبینی و تکمیل شوند.

### تغذیه و تناسب اندام بر اساس BMI (`FitnessScreen` + `FitnessResultsScreen`)

دستیار می‌پرسد کاربر ورزشکار است یا نه، هدفش از ورزش سلامتی عمومی است یا ورزش حرفه‌ای/رقابتی، و از نظر
وزن به‌دنبال کاهش، افزایش یا حفظ وزن است؛ سپس قد و وزن را می‌پرسد (با صدا یا تایپ، اعداد فارسی هم
فهمیده می‌شوند) و شاخص تودهٔ بدنی (BMI) را حساب می‌کند. بر اساس دستهٔ BMI و پاسخ‌ها، چند راهکار تغذیه و
فعالیت بدنی از `src/data/fitnessStrategies.ts` انتخاب و **با صدا خوانده می‌شود**.

دو نکتهٔ ایمنی که `engine/fitnessEngine.ts` صریحاً بررسی می‌کند:

- اگر کاربر ورزشکار باشد، BMI به‌تنهایی می‌تواند گمراه‌کننده باشد (چون توده عضلانی را نادیده می‌گیرد)؛
  این هشدار همیشه کنار نتیجه نشان داده می‌شود.
- اگر هدف وزنی با وضعیت فعلی در تضاد نگران‌کننده باشد (مثلاً کسی با کمبود وزن به‌دنبال کاهش بیشتر وزن
  است)، یک هشدار غیرمسدودکننده نشان داده می‌شود که کاربر را به پزشک/متخصص تغذیه (و در صورت نیاز، به
  بخش غربالگری سلامت روان همین اپ) ارجاع می‌دهد — بدون این‌که از نمایش راهکارهای عمومی جلوگیری کند.

### گوش فعال (`ActiveListeningScreen`)

یک قابلیت کاملاً اختیاری (پیش‌فرض خاموش) که کاربر باید صراحتاً روشنش کند. وقتی روشن و این صفحه باز
است، دستیار گفتار اطراف را با همان سرویس تشخیص گفتار (`voiceService.listen`) به متن تبدیل می‌کند و
دنبال عبارات مرتبط با درگیری/نیاز پلیس، آتش‌سوزی، وضعیت پزشکی اورژانسی، یا فشار/اجبار
(`engine/activeListeningEngine.ts#detectEmergency`) می‌گردد:

- با تشخیص **درگیری/آتش/پزشکی**، صفحه فوراً پیام مناسب را با صدا اعلام می‌کند، موقعیت مکانی فعلی را
  (در صورت مجوز) به آدرس یا مختصات تبدیل و می‌خواند، و یک دکمهٔ «تماس با ۱۱۰/۱۲۵/۱۱۵» نشان می‌دهد —
  که فقط برنامهٔ تلفن گوشی را با شماره باز می‌کند؛ تماس واقعی را باید خود کاربر تأیید کند.
- با تشخیص **فشار/اجبار**، اگر پیش‌تر (با یک گفتگوی کوتاه پرسش‌وپاسخ) نام و شمارهٔ یک «دوست مورد
  اعتماد» ثبت شده باشد، دکمه‌ای برای باز‌کردن پیامک‌رسان گوشی با متن آمادهٔ «با من تماس بگیر، فوری!»
  به آن شماره نمایش می‌دهد (`expo-sms`؛ باز هم فقط بازکردن برنامهٔ پیامک، نه ارسال خودکار).
- برای اطمینان‌خاطر در شرایطی مثل حضور پرستار بچه در منزل، کاربر می‌تواند خلاصه‌ای از گفت‌وگوهای
  شنیده‌شده را هر ۳۰ یا ۶۰ دقیقه (یا فقط دستی، با دکمهٔ «دریافت خلاصه الان») دریافت و در صورت تمایل با
  پیامک برای مخاطب ذخیره‌شده بفرستد (`summarizeListeningPeriod`).

⚠️ **محدودیت‌های حیاتی که باید بدانید** (کامل در `DISCLAIMERS.activeListeningLimitations`):

- این یک **تشخیص صوتی/آکوستیک نیست**. صدای دعوا، شعلهٔ آتش، گریهٔ کودک یا لحن صدا را نمی‌شنود؛ فقط
  جمله‌هایی را که واضح گفته شوند و درست به متن تبدیل شوند، برای عبارات کلیدی بررسی می‌کند. برای
  سناریوی «پرستار بچه»، این یعنی خلاصهٔ دوره‌ای فقط می‌تواند بگوید *چند گفت‌وگو شنیده شد* و *آیا عبارت
  نگران‌کننده‌ای در آن‌ها بود*، نه این‌که رفتار پرستار خوب بوده یا او به گریهٔ کودک بی‌توجهی کرده —
  چنین قضاوتی نیازمند مدل واقعی تشخیص صدا/رفتار است که در این اسکلت پیاده‌سازی نشده.
- فقط وقتی این صفحه **باز و در پیش‌زمینه** است کار می‌کند؛ گوش‌دادن در پس‌زمینه یا وقتی گوشی قفل است
  در این اسکلت پیاده‌سازی نشده (نیازمند سرویس بومی پس‌زمینه و خروج از Expo managed workflow است).
- این اپ **هرگز خودش و بی‌اجازه** با اورژانس تماس نمی‌گیرد یا پیامک نمی‌فرستد؛ فقط برنامهٔ تماس/پیامک
  گوشی را با اطلاعات آماده باز می‌کند و لمس نهایی همیشه با کاربر است.
- اگر قصد دارید از این قابلیت برای نظارت بر یک پرستار/مراقب استفاده کنید، بسته به کشور و ایالت ممکن
  است ضبط یا پایش صدای فرد دیگری بدون اطلاع او از نظر قانونی نیاز به رضایت یا اطلاع‌رسانی داشته باشد؛
  پیش از استفادهٔ واقعی، این موضوع را بررسی کنید.
- شماره‌های `src/data/emergencyContacts.ts` (۱۱۰/۱۲۵/۱۱۵) مخصوص ایران هستند و باید برای منطقهٔ هدف
  تأیید/به‌روزرسانی شوند.

### رفیق همراه (`CompanionScreen`)

یک فضای گفتگوی روزانهٔ کوتاه که کاربر می‌تواند اسم خودش را بگوید، چند «فکت» دربارهٔ خودش ثبت کند
(«عاشق نقاشی‌ام»، …) و حال‌وهوای امروزش را از بین ۸ حالت (غمگین، مضطرب، عصبانی، بی‌حس، درمانده، تنها،
امیدوار، آرام) انتخاب کند. دستیار:

- با صدا/نوشتار یک جملهٔ همدلانهٔ ازپیش‌نوشته‌شده متناسب با همان حال‌وهوا می‌گوید
  (`engine/companionEngine.ts#reflectionForMood`، از `data/companionResponses.ts`)،
- در صورت وجود تاریخچهٔ حال‌وهوای چند روز اخیر، یک خلاصهٔ کوتاه («این چند روز اخیر بیشتر حس … رو ثبت
  کرده بودی») می‌گوید (`summarizeRecentMoods`؛ فقط شمارش، بدون هیچ تفسیر بالینی)،
- و بسته به حال‌وهوا، یک یا دو میان‌بر به بخش‌های مرتبط اپ (موسیقی، غربالگری، تغذیه، مشاوره، رسپی،
  قصه) پیشنهاد می‌دهد.
- هر چیزی که کاربر تایپ/بگوید در یک نوار گفتگوی سادهٔ «دفترچهٔ روزانه» ثبت و با یک جملهٔ کوتاهِ تأییدی
  («شنیدمت. حرف‌هات برام مهمه.») پاسخ داده می‌شود.

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.companionNotRealAI`): این «رفیق همراه» یک مدل زبانی زنده
نیست و چیزی که کاربر می‌نویسد را واقعاً «نمی‌فهمد» — فقط اسم و فکت‌های صریحاً واردشده را روی دستگاه
ذخیره می‌کند و از بین جمله‌های از‌پیش‌نوشته‌شده، مناسب‌ترین را بر اساس حال‌وهوای انتخابی برمی‌گزیند.
هیچ درک واقعی از شخصیت، حافظهٔ گفتگویی بلندمدت، یا تحلیل احساسات از متن آزاد در این اسکلت پیاده‌سازی
نشده؛ برای یک همراه واقعاً «هوشمند»، این لایه باید به یک مدل زبانی واقعی (با رعایت کامل حریم خصوصی و
رضایت کاربر) وصل شود.

### ترک عادت (`QuitCoachScreen`)

یک صفحهٔ دوبخشی برای ترک تدریجی سیگار، الکل، مواد مخدر یا هر عادت رفتاری دیگر:

1. **راه‌اندازی**: کاربر نوع اعتیاد، میزان مصرف روزانه (اختیاری)، سال‌های عادت (اختیاری)، تعداد
   تلاش‌های قبلی (اختیاری)، محرک اصلی (استرس/جمع دوستانه/بی‌حوصلگی/روتین/میل جسمی/غیره)، و دلیل شخصی
   ترک (اختیاری) را با صدا یا تایپ وارد می‌کند. `engine/quitCoachEngine.ts#buildQuitPlan` از
   `data/quitCoachStrategies.ts` یک برنامهٔ تدریجی ۵-۶ مرحله‌ای (متناسب با نوع اعتیاد) به‌علاوهٔ یک
   قدم اضافه برای محرک انتخاب‌شده می‌سازد؛ اولین قدم با صدا هم خوانده می‌شود.
2. **چک‌این روزانه**: کاربر هر روز (حداکثر یک ثبت در روز) می‌گوید امروز مصرف داشته یا نه، سطح میل
   (۰ تا ۵)، و یک یادداشت اختیاری — همه روی دستگاه با AsyncStorage ذخیره می‌شود
   (`state/useQuitCoach.ts`). `computeStreak` تعداد روزهای متوالی بدون مصرف و میانگین میل را محاسبه
   می‌کند، و `encouragementForCheckIn` بسته به نتیجهٔ امروز یک پیام تشویقی یا دلگرم‌کننده (بدون
   قضاوت، برای روزهای لغزش هم) می‌گوید.

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.quitCoachMedicalSupervision`، همیشه برای الکل/مواد مخدر
نشان داده می‌شود): این «دستیار روزانه» جایگزین سم‌زدایی پزشکی نیست. ترک ناگهانی یا بدون نظارت الکل یا
برخی مواد می‌تواند از نظر پزشکی خطرناک باشد (حتی تشنج یا عوارض جدی)؛ برنامهٔ این بخش برای این دو نوع
عمداً کلی و محتاطانه نوشته شده و همیشه با توصیهٔ صریح مراجعه به پزشک یا مرکز ترک اعتیاد همراه است. این
اپ هیچ «بازخورد روزانهٔ» واقعی مثل نوتیفیکیشن یادآوری یا پیگیری خودکار ندارد — چک‌این کاملاً به ابتکار
خود کاربر و در همین صفحه انجام می‌شود.

### مشاور شغلی و کارآفرینی (`CareerCoachScreen`)

یک مسیر دوبخشی برای کسی که به‌دنبال شغل یا درآمد است:

1. **تشخیص روحیه**: با ۳ سؤال ساده و تراشه‌ای (نه تحلیل متن آزاد) — امنیت شغلی در برابر پتانسیل رشد،
   دنبال‌کردن دستورالعمل در برابر تصمیم‌گیری مستقل، و میزان تحمل ریسک — `engine/careerCoachEngine.ts#inferMindset`
   تشخیص می‌دهد روحیه بیشتر «کارمندی» است یا «کارآفرینی» (اکثریت ۲ از ۳ پاسخ).
2. **انتخاب مسیر**: بر اساس روحیه، ۳ مسیر پیشنهاد می‌شود — کارمندی: رزومه‌نویسی و ارسال درخواست،
   کارآموزی، مهارت‌افزایی؛ کارآفرینی: فریلنسری، راه‌اندازی کسب‌وکار، مهارت‌افزایی
   (`data/careerStrategies.ts#PATHS_BY_MINDSET`).
3. **چک‌لیست و دفترچهٔ پیشرفت**: هر مسیر یک چک‌لیست ۵ مرحله‌ای دارد (مثلاً برای فریلنسری: انتخاب
   خدمت، ساخت پروفایل، تعیین قیمت، تماس با مشتری، تحویل اولین پروژه) که کاربر خودش علامت می‌زند، به‌علاوهٔ
   یک دفترچهٔ آزاد برای ثبت روزانهٔ «امروز چه قدمی برداشتی؟» — همه روی دستگاه با AsyncStorage ذخیره
   می‌شود (`state/useCareerCoach.ts`).

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.careerCoachLimitations`): این بخش نه کارشناس استخدام واقعی
است، نه رزومهٔ کسی را می‌نویسد، نه به هیچ سایت کاریابی وصل است (این اپ اصلاً بک‌اند/اینترنت ندارد).
تشخیص روحیه فقط از ۳ پاسخ ساده است، نه یک ارزیابی روان‌شناختی واقعی. «دنبال‌کردن کاربر تا موفقیت
نهایی» با این چک‌لیست و دفترچه، به‌صورت کاملاً محلی و به ابتکار خود کاربر شبیه‌سازی شده — نه یک سیستم
واقعی یادآوری یا پیگیری خودکار.

### پیدا کردن آهنگ (`SongIdScreen`)

کاربر می‌تواند نام آهنگ، نام خواننده، یا چند کلمه‌ای که به‌خاطر دارد را با صدا یا تایپ وارد کند.
`engine/songIdEngine.ts#identifyByText` این متن را با تطبیق تقریبی (بر اساس فاصلهٔ ویرایشی
Levenshtein و بررسی زیررشته) با عنوان/خوانندهٔ کاتالوگ محلی موسیقی مقایسه می‌کند و بهترین نتیجه‌ها را
به‌همراه درصد شباهت برمی‌گرداند. برای چند آهنگ از کاتالوگ (`data/songLyricsPlaceholders.ts`)، یک
«لیریکس» نمایشی کاملاً ساختگی هم قابل‌نمایش است تا مسیر «نمایش لیریکس» در کد قابل تست باشد.

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.songIdLimitations`): این بخش هیچ فناوری واقعی تشخیص صدا یا
اثرانگشت صوتی (audio fingerprinting) ندارد — نمی‌تواند به زمزمهٔ کاربر یا کلیپ صوتی پخش‌شده گوش بدهد و
آهنگ را تشخیص بدهد؛ فقط تطبیق متنی روی اسمی است که خود کاربر می‌گوید یا تایپ می‌کند. تطبیق فقط با
کاتالوگ ساختگی همین اپ انجام می‌شود، نه اینترنت یا هیچ آرشیو واقعی، و تمام آهنگ‌ها/لیریکس‌ها کاملاً
اورجینال و غیرواقعی‌اند. برای تشخیص واقعی از روی صدا یا لیریکس واقعی،
`engine/songIdEngine.ts#audioRecognitionStub` و `#remoteLyricsProviderStub` نقطهٔ اتصال مستندشده‌ای
برای سرویس‌های دارای مجوز (ACRCloud/AudD برای تشخیص صدا، Musixmatch/Genius برای لیریکس) هستند —
هر دو عمداً پیاده‌سازی نشده‌اند و به‌جای وانمودکردن، خطای صریح می‌دهند.

### مشاور موقعیت‌های اجتماعی (`SocialAdvisorScreen`)

برای موقعیت‌هایی مثل «با مادرم سر خرید جهیزیه اختلاف داشتم و گفت بذار همسرت هم کمک مالی کنه» — کاربر
سه چیز را با چیپ انتخاب می‌کند: **رابطه** (مادر، پدر، خواهر/برادر، همسر، خانوادهٔ همسر، دوست، همکار،
شخص دیگر)، **نوع موقعیت** (مرز مالی، نصیحت ناخواسته، اختلاف‌نظر در تصمیم، تعارض سر سخاوت/کمک،
مرزگذاری کلی، انتظار خانوادگی)، و حداکثر ۳ **ویژگی شخصیتی طرف مقابل** (دست‌ودل‌باز، محتاط با پول،
کنترل‌گر، انعطاف‌پذیر، سنتی، امروزی، احساساتی، آرام) — همان چیزهایی که خود کاربر حدس می‌زند، نه چیزی
که اپ کشف کرده باشد. `engine/socialAdvisorEngine.ts`:

- `personalityInsight` از روی همان ویژگی‌های انتخابی، یک جملهٔ کوتاه «به‌نظر می‌رسد این شخص...» می‌سازد
  (فقط بازتاب انتخاب کاربر، نه یک تحلیل جدید)،
- `recommendStrategies` بر اساس تطبیق رابطه + موقعیت + همپوشانی ویژگی‌ها، از
  `data/socialStrategies.ts` بهترین راهکارها را امتیازدهی و انتخاب می‌کند — مثلاً برای
  مادر/دست‌ودل‌باز/مرز مالی، دقیقاً همان مثال جهیزیه با یک پاسخ نمونه پیشنهاد می‌شود.

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.socialAdvisorLimitations`): این بخش هیچ‌کس دیگری را واقعاً
نمی‌شناسد و شخصیت واقعی هیچ فردی را تحلیل نمی‌کند — فقط بر اساس برچسب‌هایی که خود کاربر برای طرف مقابل
انتخاب می‌کند، چند راهکار کلی و از‌پیش‌نوشته‌شده پیشنهاد می‌دهد؛ این یک ارزیابی روان‌شناختی واقعی از آن
فرد نیست. برای موقعیت‌های شامل کنترل شدید، تهدید یا آسیب عاطفی/جسمی، این بخش کافی نیست — بخش «مشاورهٔ
زناشویی و روابط» یا کمک حرفه‌ای مناسب‌تر است.

### پیدا کردن هدیهٔ مناسب (`GiftAdvisorScreen`)

کاربر با چیپ رابطهٔ خود با گیرنده (مادر، پدر، خواهر/برادر، همسر، …)، ردهٔ سنی، مناسبت (تولد، عروسی،
فارغ‌التحصیلی، تسلیت، …)، بودجه، و حداکثر ۳ علاقهٔ گیرنده (کتاب‌خوانی، آشپزی، ورزش، فناوری، …) را
انتخاب می‌کند. `engine/giftAdvisorEngine.ts#recommendGiftIdeas` ابتدا ردهٔ سنی را به‌عنوان یک فیلتر
سخت‌گیرانه اعمال می‌کند (هیچ‌وقت ایدهٔ نامناسب سنی پیشنهاد نمی‌شود)، سپس بر اساس همپوشانی مناسبت،
بودجه و علایق از `data/giftIdeas.ts` بهترین ایده‌ها را امتیازدهی می‌کند. برای علاقهٔ «کتاب‌خوانی»،
پیشنهاد همیشه یک **ژانر یا موضوع کلی** است (مثلاً «یک رمان معاصر خوش‌نام»)، نه اسم یک کتاب یا نویسندهٔ
واقعی مشخص.

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.giftAdvisorLimitations`): این بخش به هیچ فروشگاه یا کاتالوگ
واقعی محصول وصل نیست — قیمت، موجودی، یا لینک خرید واقعی وجود ندارد؛ همهٔ ایده‌ها ساختگی و کلی‌اند.
پیشنهادهای کتاب هم عمداً فقط ژانر معرفی می‌کنند، نه یک عنوان مشخص، چون این اپ به کاتالوگ زندهٔ کتاب‌ها
دسترسی ندارد و نمی‌خواهد با اطمینان کاذب یک عنوان نادرست یا قدیمی پیشنهاد بدهد. بهترین هدیه‌ها معمولاً
از شناخت واقعی و شخصی خود کاربر می‌آید؛ این پیشنهادها فقط نقطهٔ شروعی برای الهام‌گرفتن هستند.

### خانواده و اطرافیان (`FamilyCircleScreen`)

پاسخ به این نیاز که دستیار «اعضای خانواده و اطرافیان تأثیرگذار» کاربر را بشناسد: کاربر می‌تواند برای
هر فرد (مادر، پدر، خواهر/برادر، همسر، خانوادهٔ همسر، دوست، همکار، یا هرکس دیگر) یک پروفایل کوچک بسازد
— اسم، نوع رابطه، حداکثر ۳ ویژگی شخصیتی (همان واژگان مشاور موقعیت‌های اجتماعی)، و یک یادداشت آزاد —
که روی دستگاه با AsyncStorage ذخیره می‌شود (`state/useFamilyCircle.ts`). نکتهٔ اصلی این بخش، اتصال
مستقیم به مشاور موقعیت‌های اجتماعی است: با زدن دکمهٔ «راهکار برای این فرد» روی هرکدام از افراد
ذخیره‌شده، صفحهٔ `SocialAdvisorScreen` با رابطه و ویژگی‌های همان فرد از قبل پر می‌شود
(`navigation.navigate("SocialAdvisor", { presetRelation, presetTraits, presetName })`) — یعنی کاربر
لازم نیست هر بار از نو رابطه و شخصیت طرف مقابل را وارد کند.

⚠️ **محدودیت حیاتی** (کامل در `DISCLAIMERS.familyCircleLimitations`): این بخش هیچ‌کس را واقعاً
نمی‌شناسد، هیچ مکالمه یا رفتار واقعی را زیر نظر ندارد، و هیچ ارزیابی روان‌شناختی واقعی انجام نمی‌دهد —
فقط یک نام و چند برچسبی که خود کاربر انتخاب کرده، روی همین دستگاه ذخیره می‌شود. برای روابط خانوادگی
پیچیده یا آسیب‌زا، این پروفایل‌های ساده کافی نیستند؛ بخش «مشاورهٔ زناشویی و روابط» یا کمک حرفه‌ای
مناسب‌تر است.

### دستیار کارهای شخصی (`PersonalTasksScreen`)

کاربر یک «مخاطب سریع» (اسم + تلفن و/یا ایمیل، اختیاری) ذخیره می‌کند، سپس با صدا یا تایپ فرمانی مثل
«به مامان پیامک بده بگو دیر میام» می‌دهد. `engine/personalTaskEngine.ts#parseIntent` نوع کار (ایمیل،
پیامک، تماس، واتساپ)، نام مخاطب، و متن پیام را با تطبیق کلیدواژه/الگوی ساده تشخیص می‌دهد (نه NLU
واقعی)، `resolveContact` مخاطب را از بین «مخاطبین سریع» ذخیره‌شده پیدا می‌کند، و اگر چیزی کم باشد
(مخاطب، شماره، ایمیل، یا متن پیام)، صفحه با چیپ از کاربر می‌پرسد. وقتی همه‌چیز آماده شد، یک پیام تأییدی
صوتی/نوشتاری («آیا اجازه می‌دی...؟») نمایش داده می‌شود؛ فقط بعد از تأیید صریح کاربر،
`buildActionUrl` آدرس مناسب (`mailto:`, `sms:`, `wa.me`) ساخته و برنامهٔ بومی مربوطه با
`Linking.openURL` (یا برای پیامک، `expo-sms`) باز می‌شود — دقیقاً با همان الگوی امن قابلیت «گوش فعال».

**کاهش تعداد تاییدها بدون تغییر مرز ایمنی**: هر «مخاطب سریع» یک پرچم «مورد اعتماد» دارد که خود کاربر
با یک لمس روشن/خاموش می‌کند. برای مخاطب مورد اعتماد، اگر فرمان از قبل کامل باشد (کار + مخاطب + متن —
مثلاً یک فرمان صوتی کامل)، صفحه پرسش تاییدِ خودش را حذف می‌کند و مستقیم برنامهٔ مربوطه را باز می‌کند؛
اگر چیزی برای تکمیل لازم باشد، به‌جای سؤال «آیا اجازه می‌دی؟»، فقط یک دکمهٔ ساده‌تر «انجام بده» نشان
داده می‌شود. این تغییر فقط مرحلهٔ تاییدِ **داخل همین اپ** را حذف می‌کند؛ برنامهٔ سیستم‌عامل هنوز باز
می‌شود و لمس نهاییِ ارسال/تماس همچنان با خود کاربر و داخل همان برنامه است — چون این بخش قابل تغییر از
سمت این اپ نیست (نگاه پایین).

⚠️ **محدودیت حیاتیِ عمدی، و بخشی هم واقعاً قانون سیستم‌عامل** (کامل در
`DISCLAIMERS.personalTasksLimitations`): این بخش **هرگز** به‌جای کاربر ایمیل/پیامک نمی‌فرستد یا تماس
برقرار نمی‌کند — فقط برنامهٔ مربوطهٔ گوشی را با محتوای آماده باز می‌کند و لمس نهاییِ «ارسال»/«تماس»
همیشه با خود کاربر و داخل همان برنامه است. این فقط یک انتخاب طراحی نیست: اپل اصلاً اجازهٔ ارسال خودکار
پیامک یا برقراری تماس بدون بازشدن اپ خودش را به هیچ اپی نمی‌دهد، و گوگل هم چنین اجازه‌ای را فقط به
اپی می‌دهد که «اپ پیش‌فرض پیامک‌رسان» گوشی باشد. این اپ به حساب ایمیل واقعی، تاریخچهٔ پیامک واقعی،
لاگ تماس، یا مخاطبین واقعی گوشی دسترسی ندارد — فقط «مخاطبین سریع»ی که خود کاربر اینجا ذخیره کرده در
دسترس‌اند. این بخش نمی‌تواند به «هر اپلیکیشنی» وصل شود؛ فقط اپ‌هایی با یک آدرس بازکردنیِ عمومی (ایمیل،
پیامک، تلفن، واتساپ) پشتیبانی می‌شوند. تنها مسیر واقعی برای ارسال خودکارِ ایمیل بدون هیچ تاییدی، ورود
واقعی با حساب گوگل و اجازهٔ Gmail است — یک تاییدِ یک‌باره در صفحهٔ رسمی گوگل، نه در این اپ؛ این مسیر
در `engine/personalTaskEngine.ts#realAutomationStub` مستند شده ولی عمداً پیاده‌سازی نشده و به‌جای
وانمودکردن، خطای صریح می‌دهد.

### مشاور حقوقی و آگاهی از سلامت روان (`LegalAdvisorScreen` + `MentalHealthAwarenessScreen`)

دو کتابخانهٔ محتوای کوچک و از‌پیش‌نوشته‌شده، هرکدام ۳۰ موضوع (یک تقویم محتوایی ماهانه)، با یک
UI مشترک قابل جستجو (`components/AdvisoryTopicBrowser.tsx`):

- **مشاور حقوقی** (`data/legalTopics.ts`): موضوعات رایج حقوقی روزمره — طلاق و مهریه، حضانت و نفقه،
  ارث و وصیت، چک و سفته، حقوق مستاجر و کارگر، تصادف و دیه، جرائم رایانه‌ای، ملک و قرارداد و... .
- **آگاهی از سلامت روان** (`data/mentalHealthTopics.ts`): نشانه‌های رایج افسردگی، اضطراب، اختلال
  دوقطبی، OCD، ADHD، فرسودگی شغلی، اعتیاد، PTSD و... — هم در خودِ کاربر، هم در نزدیکان درجه‌یک
  (پدر، مادر، همسر، خواهر و برادر).

هر دو، همان الگوی صداقتِ کل اپ را دنبال می‌کنند: این‌ها **کتابخانهٔ مرجعِ از‌پیش‌نوشته‌شده‌اند، نه
یک وکیل یا روان‌شناس واقعی** و نه یک گفتگوی زندهٔ هوش مصنوعی — `engine/advisoryContentEngine.ts`
فقط بین متن‌های آماده جستجوی کلیدواژه‌ای انجام می‌دهد (`searchTopics`)، تحلیل یا تشخیصی در کار
نیست. `DISCLAIMERS.legalAdvisorLimitations` و `DISCLAIMERS.mentalHealthAwarenessLimitations` این
محدودیت را صریح می‌گویند و بالای هر دو صفحه نمایش داده می‌شوند؛ دیسکلیمر سلامت روان، در نشانه‌های
خطر جدی، صریحاً کاربر را به اورژانس ۱۱۵ ارجاع می‌دهد.

محتوای این دو کتابخانه از همان تقویم محتوایی یوتیوب تولید شده (`../content-calendars/`) و نسخهٔ
یکسانی از آن روی بک‌اند هم ذخیره شده (`GET /skills/legal` و `GET /skills/mental_health` — نگاه
کنید به `backend/README.md`)؛ خودِ اپ همچنان آفلاین و بدون نیاز به بک‌اند کار می‌کند چون محتوا در
همین دو فایل داده هم باندل شده است.

### حساب کاربری و همگام‌سازی ابری (اختیاری)

ورود کاملاً اختیاری است — همهٔ بخش‌های بالا بدون ورود هم فقط روی همین گوشی (`AsyncStorage`) کار
می‌کنند، دقیقاً مثل قبل. اگر بخش «تنظیمات» → «ورود برای پشتیبان‌گیری ابری» انتخاب شود،
`LoginScreen` یک جریان دومرحله‌ای شمارهٔ موبایل + کد یک‌بارمصرف را نشان می‌دهد که به بک‌اند واقعی
پروژه (پوشهٔ `../backend`، مستقل از این اپ) وصل می‌شود. جزئیات پیاده‌سازی:

- `services/apiConfig.ts` آدرس بک‌اند را از `EXPO_PUBLIC_API_BASE_URL` می‌خواند (پیش‌فرض
  `http://localhost:4000` که فقط برای وب/شبیه‌ساز روی همان کامپیوتر کار می‌کند — برای دستگاه واقعی
  باید IP شبکهٔ محلی یا آدرس دیپلوی‌شده تنظیم شود).
- `services/tokenStorage.ts` توکن‌های JWT را (زیر کلید جدا `yavar_auth_tokens_v1`) نگه می‌دارد؛
  `services/apiClient.ts` هر درخواست را با `Authorization: Bearer` امضا می‌کند و روی خطای ۴۰۱ یک‌بار
  توکن را تازه (`refresh`) کرده و درخواست را دوباره می‌فرستد.
  `state/AuthContext.tsx` وضعیت ورود را در کل اپ در دسترس می‌گذارد.
- `services/syncStorage.ts` جایگزین یک‌به‌یکِ `AsyncStorage.getItem/setItem/removeItem` است که ۹ از
  ۱۰ هوک state (همه به‌جز `useWardrobe` — چون عکس کمد لباس فقط مسیر فایل محلی دستگاه است و معنایی
  در همگام‌سازی بین‌دستگاهی ندارد) از آن استفاده می‌کنند: خواندن همیشه محلی و آفلاین-first است؛
  نوشتن ابتدا محلی ذخیره می‌شود (UI هرگز منتظر شبکه نمی‌ماند) و سپس best-effort به بک‌اند ارسال
  می‌شود — دقیقاً همان الگوی «ذخیرهٔ best-effort» که هر هوک از قبل داشت. بعد از ورود موفق،
  `fullSyncOnLogin()` ابتدا هرچه محلی موجود است را به سرور push می‌کند (تا دادهٔ همان دستگاه از
  بین نرود) و سپس همهٔ کلیدها را از سرور می‌خواند و جایگزین محلی می‌کند (برای بازیابی روی دستگاه
  دوم یا بعد از نصب مجدد) — آخرین نوشته برنده است، بدون ادغام واقعی؛ برای دادهٔ کوچک و
  عمدتاً تک‌دستگاهیِ این اپ کافی است.
- `DISCLAIMERS.cloudSyncLimitations` این رفتار را کامل و صادقانه توضیح می‌دهد (چه چیزی سینک
  می‌شود، چه چیزی نمی‌شود، و این‌که سرور فقط ذخیره می‌کند، تحلیل نمی‌کند) و در صفحات ورود و
  تنظیمات نمایش داده می‌شود.

## اجرا

```bash
npm install
npm run web       # اجرای نسخهٔ وب
npm run ios       # نیازمند Xcode/شبیه‌ساز iOS یا Expo Go
npm run android    # نیازمند Android Studio/شبیه‌ساز یا Expo Go
npm run start      # منوی Expo Dev Tools (انتخاب پلتفرم از آنجا)

npm run test        # تست‌های Jest برای موتورها + سرویس‌های ورود/همگام‌سازی
npm run typecheck   # بررسی نوع با TypeScript
npm run generate:synthetic   # تولید کاربران ساختگی و چاپ نتیجهٔ موتور در کنسول
```

برای فعال‌کردن ورود/همگام‌سازی ابری، یک فایل `.env` بسازید و بک‌اند واقعی (`../backend`، طبق
`backend/README.md`) را اجرا کنید:

```bash
echo "EXPO_PUBLIC_API_BASE_URL=http://localhost:4000" > .env   # وب/شبیه‌ساز روی همین کامپیوتر
# روی گوشی واقعی: به‌جای localhost از IP شبکهٔ محلی کامپیوتر یا آدرس دیپلوی‌شدهٔ بک‌اند استفاده کنید
```

## نکات فنی مهم

- **صدا**: `expo-speech` برای تبدیل متن‌به‌گفتار روی هر سه پلتفرم کار می‌کند. تشخیص گفتار
  (speech-to-text) فقط در مرورگرهایی با پشتیبانی از Web Speech API (مثل Chrome) فعال است؛ روی
  iOS/Android به‌صورت خودکار غیرفعال است و کاربر باید تایپ کند — برای افزودن STT بومی واقعی،
  پکیجی مثل `expo-speech-recognition` یا یک API ابری را پشت همین `VoiceService` وصل کنید.
- **موسیقی**: کاتالوگ در `musicCatalog.ts` عمداً فقط داده (متادیتا) است، به‌جز یک تُن صوتی تولیدشده
  که برای اثبات صحت مسیر پخش (`expo-av`) گنجانده شده. در تولید واقعی این بخش باید به یک سرویس
  موسیقی دارای مجوز وصل شود.
- **حریم خصوصی**: تمام دادهٔ هر بخش (یادداشت خلق‌وخو، مخاطبین، پروفایل‌ها و...) به‌صورت پیش‌فرض فقط
  روی همین گوشی (`AsyncStorage`) ذخیره می‌شود و با بستن اپ از بین نمی‌رود. تنها در صورتی که کاربر
  آگاهانه وارد حساب شود، نسخه‌ای از همین دادهٔ متنی (نه عکس‌های کمد لباس) به‌صورت خصوصی روی بک‌اند
  پروژه هم ذخیره می‌شود — دقیقاً طبق توضیح بالا («حساب کاربری و همگام‌سازی ابری») و
  `DISCLAIMERS.cloudSyncLimitations`. برای استفادهٔ واقعیِ گسترده، رضایت کاربر (consent) صریح‌تر و
  انطباق با قوانین حریم خصوصی داده‌های سلامت (مثل HIPAA/GDPR) باید جداگانه طراحی شود.

## گام‌های بعدی برای تبدیل به محصول واقعی

1. بازبینی بالینی کامل بانک سؤال و آستانه‌های امتیازدهی توسط متخصص سلامت روان.
2. جایگزینی امتیازدهی ابتکاری با مدل/مقیاس‌های دارای مجوز و اعتبارسنجی‌شده.
3. اتصال STT بومی واقعی (iOS/Android) و یک سرویس موسیقی دارای مجوز.
4. طراحی مسیر تشدید انسانی (human escalation) واقعی برای موارد بحرانی، نه فقط UI.
5. پیاده‌سازی ذخیره‌سازی امن، رضایت‌نامه، و انطباق قانونی/رگولاتوری منطقه هدف.
